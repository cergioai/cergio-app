# Cergio OS v2 — binding every micro-feature to the spec

**For Tarik. 2026-08-01. Goal: certainty before soft launch.**

---

## The gap in v1

v1 gave you a constitution, subagents, gates that can fail, and spend gates. Good — but
it still can't answer the one question that matters before a soft launch:

> **"Which parts of my product are PROVEN to work, right now?"**

Today the honest answer is: nobody knows. There is a `FROZEN_SPEC.md` with the agreed
behaviour, and 183 QA gates — but **nothing connects them.** A spec line can exist with no
gate. A gate can exist for behaviour nobody agreed to. Neither situation is visible. That
gap is exactly where drift lives.

---

## The fix: a SPEC REGISTRY — one row per micro-feature

One machine-checked file. Every micro-feature is a row, and a row is only **PROVEN** when
all four columns are real:

| SPEC ID | Behaviour (one line, plain English) | Gate | Live proof | Status |
|---|---|---|---|---|
| S-014 | Signed-in user clicking "Claim founding spot" lands on the listing flow, never the login screen | qa #158 | screenshot 2026-08-01 | PROVEN |
| S-021 | A crawl source that spends $1 with no leads stops automatically | qa #185 | ledger row | PROVEN |
| S-033 | Provider sees a paid booking end-to-end | — | — | **NOT PROVEN** |

**Four states, no others:**

- **PROVEN** — spec line + gate (mutation-tested) + live artifact. Trustworthy.
- **CODED** — code exists, gate exists, but never proven live. *Not* trustworthy.
- **UNGUARDED** — spec line with no gate. This is where regressions come from.
- **ORPHAN** — gate with no spec line. Someone built something nobody agreed to.

---

## The drift detector

A gate whose only job is to police the registry. It **fails the build** if:

1. a `FROZEN_SPEC.md` line has no SPEC ID in the registry → **UNGUARDED**
2. a registry row has no matching qa gate → **UNGUARDED**
3. a qa gate maps to no registry row → **ORPHAN**
4. a row claims PROVEN with no live-proof artifact → **false green**

This is the actual binding you asked for. Spec and code are welded: neither can move
without the other, and the build stops if they separate.

---

## Definition of Done — a micro-feature is not done until all five

1. **Spec line** — one sentence in plain English, in `FROZEN_SPEC.md`, with an ID
2. **Code** — one PR, revertible on its own
3. **Gate** — mutation-tested (break it, watch it FAIL, restore it)
4. **Live proof** — screenshot, HTTP status, or DB row, dated
5. **Registry row** — status flipped to PROVEN

Miss any one and it is not done. No exceptions — 9 of my gates last night were green and
incapable of failing, and 6 crawl sources reported success while writing nothing.

---

## WIP limit: ONE

**Exactly one micro-feature in flight at a time.** Not two. This single rule removes the
biggest regression source there is — simultaneous changes, where a break can't be
attributed to a cause. It is also why last night went badly: I had six things moving and
could not tell which fix did what.

## Soft-launch readiness board

One number, published every cycle, that you can read in five seconds:

```
SOFT LAUNCH READINESS      7 / 34 PROVEN  (21%)
  PROVEN      7   ← trustworthy
  CODED      19   ← exists, never proven live
  UNGUARDED   6   ← regression risk
  ORPHAN      2   ← built but unagreed
  BLOCKER     1   ← paid booking never demonstrated
```

You stop guessing whether the product is ready. You read the number.

## What else I propose (beyond what you asked)

1. **A "no simultaneous changes" hard rule.** WIP = 1, enforced by me, visible in the
   registry (only one row may be IN-PROGRESS).
2. **Every PR revertible alone.** No PR may bundle two micro-features. Recovery becomes
   one action instead of an investigation.
3. **A weekly regression sweep** — re-run every PROVEN row's live proof, because PROVEN
   decays. A screenshot from three weeks ago is not evidence today.
4. **Kill the stale-PR backlog.** There are 21 open PRs, several months old. They are
   noise that hides real signal and they periodically deadlock the merge queue — which
   silently blocked four fixes for two hours today.
5. **One report, not many.** Currently: GROWTH-STATUS, ops-metrics, qa findings, UX
   suggestions. Collapse to a single dated status page: readiness number, spend ledger,
   per-source table, blockers.
6. **A written escalation rule.** Anything I cannot verify myself (payments, passwords,
   vendor account state) gets surfaced as a named founder action with the exact click
   path — not buried in prose.
